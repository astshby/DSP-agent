# OpenAI 与 DeepSeek 接入：推荐工程形态

状态：离线 v0.9 / 第 9 次已交付。本地 HTTP 服务、工具契约、受限模拟 Runner 和启动脚本已实现；真实模型、设置页面、密钥持久化及供应商 SDK 适配尚未实现或联调。第一家为 OpenAI API，第二家为 DeepSeek API，分别安排第 10、11 次。本文保留最终架构方案；当前实际接口见《任务与工具接口》。

## 1. 推荐结构

采用本地网页应用：HTML/JavaScript 界面、Node.js 本地后端、共享 DSP 模块、OpenAI Agents SDK for JavaScript，以及两个模型服务配置。

```text
网页：输入信号、选择参数、输入自然语言、绘图
  │ 同源 HTTP 请求 / 结果事件
本地 Node.js 后端
  ├─ 提供网页和 API
  ├─ 读取本机模型配置与密钥
  ├─ 管理信号、实验结果和运行状态
  ├─ Agent Runner：模型 → 工具调用 → 执行结果 → 模型
  ├─ OpenAI / DeepSeek 模型适配
  └─ 调用共享 DSP 函数
       │
       └─ 同一份 DSP 函数也供纯离线网页使用
```

Agent Runner 是本机程序中的一段运行逻辑，SDK 帮助管理模型请求、工具执行与多轮历史。模型供应商提供推理服务；项目定义自己的 DSP 工具和规则。无需另外安装一个能操作整个电脑的通用 Agent。

OpenAI API 接入与使用 ChatGPT 聊天产品是不同入口，需要 API 凭据及可用额度；不会将当前聊天会话、记忆和所有内置工具直接搬入课程网页。

## 2. 用户最终如何启动和配置

保留两种运行入口，使用同一套界面组件和 DSP 核心：

1. **纯离线演示**：双击打包后的 HTML，直接生成/导入信号并分析，无需后端或 API Key。
2. **模型模式**：双击启动脚本，脚本启动本机 Node.js 服务并打开浏览器。服务同时提供网页和 `/api/...`，示意地址为 `http://127.0.0.1:3210`。这些启动脚本与地址目前是设计，不是已经运行的服务。

普通 HTML 文件不能自行启动一个本机 Node.js 进程。使用启动脚本可以让用户仍然只需双击一次，同时避免将 `file://` 页面跨域连接后端作为主交付路径。本地服务启动后，手动分析仍能在断网情况下工作；选择云端模型时需要相应网络连接。

页面的“模型设置”提供：

| 字段/操作 | 设计 |
| --- | --- |
| 服务商 | OpenAI / DeepSeek，各自保存配置 |
| API 地址 | 官方预设；高级设置中可编辑 |
| 模型 | 手动填写已确认可用的模型 ID；模型列表读取为可选便利功能 |
| API Key | 密码输入框，提交到本机后端保存 |
| 协议 | 由服务商预设决定；高级设置允许显式选择 Responses 或 Chat Completions |
| 验证 | 先验证真实模型请求，再验证一次简单工具调用；显示对应结果 |
| 使用 | 选择当前服务商；更换服务商不会改变信号和算法 |

不能把“地址能连通”当成“密钥、模型和工具调用都能用”。验证按钮的模型请求可能产生少量 API 费用，界面应说明。

## 3. 密钥保存在哪里

课程首版建议由本地后端将设置保存到当前用户的应用配置目录，采用两个文件：

- `providers.json`：服务商 ID、地址、模型、协议和能力标记。
- `secrets.json`：每个服务商的 API Key，仅允许当前用户访问。

这两个文件放在项目之外，例如用户目录下的 `.dsp-agent/`，不进入 GitHub 和课程提交包。Unix 系统使用目录/文件权限限制访问；Windows 使用当前用户访问权限。本地 JSON 文件不是加密保险箱，后续可将密钥部分换成系统凭据库，界面和模型调用代码无需随之更改。

网页仅在用户输入密钥时临时持有该值，将其发给本机后端后清空输入框。查询设置只返回“已配置”、服务商和模型等信息；不回传真实 Key，不存入 localStorage，不写入日志或实验导出文件。后端调用选定模型服务时才附加该服务的认证头。

服务只监听本机回环地址；检查 Host 和 Origin，对更改配置及启动模型任务的请求做本机会话校验。模型工具不提供修改密钥或服务商配置的能力。

## 4. 一次自然语言请求的完整流程

以“对当前信号做 100 Hz 低通，再画频谱”为例：

1. 用户已经在浏览器中生成或导入信号。第一次使用模型时，前端将该信号及采样信息登记到本机后端，获得 `signalId`。数据修改后生成新版本，避免模型引用旧数据。
2. 前端提交 `POST /api/agent/runs`，正文包含 `providerId`、`signalId`、用户文字和可选会话 ID，不包含 API Key。
3. 后端读取所选服务的配置，向模型发送用户文字、当前信号摘要、已实现的工具定义与使用规则。
4. 模型返回工具调用，例如请求运行 FIR 低通及频谱分析。工具调用携带函数名、结构化参数和调用 ID。
5. 本地 Runner 校验参数、当前信号的访问范围及 DSP 约束，然后执行本地函数。云端模型无需连接用户电脑的本地端口。
6. DSP 函数产生真实数组与指标；后端保存完整结果，将结果 ID 和摘要返回模型，并通过事件通知网页读取结果并绘图。
7. Runner 将工具结果作为下一轮输入发送给模型。模型可以继续调用工具、请求用户补充参数，或输出结果解释。
8. 网页显示处理步骤、实际图形、关键指标和模型解释。图表数据来自 DSP 执行结果。

完整信号和结果数组留在浏览器/本机后端；发往云端的内容默认仅为用户文字、信号元数据、工具参数和结果摘要。使用 SDK 时关闭不需要的外部 tracing，避免额外上传执行记录。

建议的最小本地 API：

| 接口 | 用途 |
| --- | --- |
| `GET /api/providers` | 读取不含密钥的配置及“已配置”状态 |
| `PUT /api/providers/:id` | 保存用户输入的配置或替换密钥 |
| `POST /api/providers/:id/test` | 执行模型/工具调用验证 |
| `POST /api/signals` | 登记本机信号并返回 ID |
| `POST /api/agent/runs` | 启动一次 Agent 任务，返回运行 ID |
| `GET /api/agent/runs/:id/events` | 接收状态、文字、工具结果与完成/错误事件 |
| `POST /api/agent/runs/:id/cancel` | 取消仍在进行的任务 |
| `GET /api/results/:id` | 获取实际绘图数据与指标 |

这些 HTTP 接口供网页使用。模型看到的是工具定义，不需要知道完整网页结构或每个 HTTP 路由。

## 5. DSP 工具如何定义

首版只需要两个工具：

- `get_signal_info`：返回当前信号的采样率、长度、数据类型等信息。
- `run_analysis`：接受统一的分析任务，执行已经实现的操作序列，返回结果摘要和结果 ID。

`run_analysis` 调用的仍是手动模式使用的 `runAnalysis(task)`。将算法写成无 DOM 依赖的纯 JavaScript/TypeScript 模块，分别供浏览器和 Node.js 引入。绘图留在浏览器；算法与参数校验只维护一份。

SDK 的 `tool({ name, description, parameters, execute })` 将四件事对应起来：模型看到工具名称、用途、参数格式；本机执行 `execute` 内绑定的 DSP 函数。此模式在官方示例中已有完整实现。

模型需要明确的操作白名单、参数单位、范围、缺失参数处理规则，以及当前数据摘要。只把函数代码放到服务器上并不会让模型自动知道它的存在；每次请求需由 SDK/适配器传递相应工具定义。

## 6. 输入输出不匹配如何解决

有三层不同的契约：

1. **网页与本机后端**：我们自己定义和版本化的 HTTP/JSON 接口。
2. **Runner 与模型服务**：使用 SDK 的 Responses/Chat Completions 模型适配器，保留各服务所需的历史与工具调用关联信息。
3. **模型与 DSP 工具**：参数结构校验加 DSP 语义校验，例如 `0 < cutoffHz < fs/2`。

OpenAI 首先考虑官方 Responses 路径；DeepSeek 先验证其 OpenAI 兼容工具调用路径，使用相应的 Chat Completions 或经验证的 Responses 适配器。协议选择与模型能力以实际验证为准，不假设只改地址和 Key 就能兼容所有功能。

初版仅使用普通函数工具，不依赖服务商专属搜索、浏览器操作或代码执行工具。结构化输出/strict 参数、推理模式、流式工具参数和并行调用能力分别验证；不支持的选项由适配层关闭，但本地参数校验始终执行。

格式错误、未知工具、缺失采样率、非法截止频率等，都转换成明确错误。可允许一次有限纠正，仍失败则停止本次任务并显示原因。为运行设置轮次、工具次数和超时上限；取消按钮应终止后续调用。

鉴权失败、额度不足、网络错误与 DSP 参数错误分开显示。可以回退到用户选择的手动/规则模式；不能把模拟响应标成真实模型结果，也不自动将对话发送到另一家服务。

## 7. 不接模型时的能力

手动模式是表单数值 → 参数校验 → DSP 运算 → 绘图，不需要文字识别。

规则助手才会识别“卷积”“低通 100 Hz”等固定表达。参考案例目前识别操作关键词，具体序列来自表单。

模型助手新增的是：理解较自由的表达、依据工具说明组织多步操作、利用结果决定下一步、识别缺失信息并追问。底层算法与实验结果的可信依据保持相同。

## 8. 后移模型接入并控制交付风险

正式交付调整为第 14 周（第 10 次）OpenAI、第 15 周（第 11 次）DeepSeek。前六次集中完成第二章；统一 DSP 与任务入口从第一版保留，模型工程在后段开展：

| 时间 | 提前完成的最小验证 |
| --- | --- |
| 第 5—10 周 / 第 1—6 次 | 统一任务入口和独立 DSP 模块；完成第二章的本地实验，不安排模型联调 |
| 第 11—12 周 / 第 7—8 次 | DFT/FFT 与数字滤波器设计；继续通过同一入口验证 |
| 第 13 周 / 第 9 次 | 离线结项与规则助手；准备本地后端、工具契约和模拟执行；凭据可用时两家各验证一次短工具调用 |
| 第 14 周 / 第 10 次 | 完成 OpenAI 页面配置、完整分析任务、结果解释和异常处理 |
| 第 15 周 / 第 11 次 | 完成 DeepSeek 对等流程、服务商切换、同任务对比与最终交付 |

第 9 次的真实验证只测试一条简短工具调用链，以提前暴露服务兼容问题；没有真实凭据时可以做模拟验证，但两家模型的兼容性仍记为未验证。最后一次不增加新的 DSP 算法，时间优先用于第二家服务与回归。

## v0.9.1 补充：离线交互与官方 API

离线规则助手已增加自然句式、Hz/kHz 参数提取、页面默认值和对已有滤波/频谱步骤的修改。计划中会标出参数来源，执行时复用原任务与 DSP 入口。这些交互在第 10、11 次真实模型接入时继续使用。

两家默认均使用官方 API。ChatGPT Plus/Pro 订阅不包含 OpenAI API 额度；聊天产品的账号权益不直接转成自建网页的 API 权益。API 平台单独创建 Key 和计费。DeepSeek 也需核对官方开放平台的 Key 与余额。账号、官方入口、费用边界和本次无法实时访问官方页面的限制见 [API 账号与接入说明](API账号与接入说明.md)。
